# 轻食记 V1：产品与交互设计

版本：2026-10-01。交付范围：设计方案与静态效果图；尚未开发。

## 1. 产品目标与原则

面向希望减少手动记餐操作的 iPhone 用户。以 iOS 27 为目标系统，拍摄餐食后，通过视觉大模型识别食物、估算份量与热量，保留可编辑的每餐历史。

核心体验：拍照 → 分析 → 确认实际摄入 → 保存。默认不要求用户称重；允许自行补充克重、食物品牌、烹饪方式和吃下的比例。所有热量显示为估算，不将照片识别包装为精准测量。

优先减少输入和页面层级。核心记录无需注册应用账号。不自建业务服务器；在线模型服务仍属于第三方云服务，不能称为完全离线。

## 2. 页面结构

底部两个入口：今天、历史。拍照为首页主按钮，设置入口置于右上角。

- 今天 → 拍照/相册 → 照片确认 → 分析 → 结果确认 → 保存 → 餐食详情。
- 今天的餐食列表 → 餐食详情 → 编辑。
- 历史 → 日期 → 当日餐食 → 餐食详情。
- 设置 → 模型服务、苹果健康、存储与导出、隐私。

拍照、照片确认、识别中和编辑均属于记录流程，不占用底部导航。

## 3. 今天页

顶部：今天、日期、设置。中心突出“今日已记录摄入”，避免将未记录的餐食视为零摄入。用户未设置目标时不出现目标进度条；设置后展示手动目标及进度，不自动给出减重处方。

主操作：拍照记录这一餐。次操作：从相册选择。底部餐食列表按时间排序，显示餐次、时间、缩略图、食物摘要和总热量；加餐可记录多次。

空状态：一句“拍下第一餐，开始记录”，保留拍照和相册入口。已有数据时显示早餐、午餐、晚餐、加餐的实际记录，不展示一排无意义的空卡片。

正在分析的餐显示“分析中”，不计入今日已记录摄入。待确认结果显示“待确认”，可返回继续确认。已保存餐食才计入统计。

## 4. 拍照与照片确认

相机页：返回、闪光灯、取景区域、快门、相册入口。提供一行提示“尽量拍全食物；多人餐请标明你吃的部分”。权限在第一次进入相机时请求，拒绝后可继续使用相册或手动记录。

照片确认页：照片预览、重拍、添加另一张照片、开始分析。V1 建议同一餐最多三张照片，明确标注“同一餐补充照片”，模型需合并视角，不能重复计算同一盘食物。

餐次根据当前时间预选，允许修改；餐食时间默认当前时间。相册中的旧照片也要求确认餐食日期，不把拍摄时间直接当作进食时间。

可选补充输入：“一人份，米饭剩了一半”“两个人共享，只记录我的部分”。用户无需填写也能继续。

## 5. 识别中与失败处理

展示真实任务状态，例如上传中、分析中；没有实际阶段反馈时只显示“正在分析”，不伪造百分比或倒计时。用户可返回其他页面；后台执行受 iOS 限制，不能保证持续运行。

无网络：保留本机草稿，提供稍后重试和手动记录；不承诺系统自动在后台完成。

服务超时/额度不足/鉴权失败：照片和补充文字不丢失，分别显示可理解的原因及重试或配置服务入口。重试复用本餐草稿，不能新增一条重复餐食。

照片模糊或没有食物：提示重拍；保留手动记录入口。无法判断某一项时，只标记那一项，不能将未知食物默认为零热量。

## 6. 分析结果与确认页

这是核心页面。信息顺序：餐次与时间 → 原照片 → 本餐估算合计 → 食物清单 → 关键疑问 → 保存按钮。

每项食物显示：名称、估算份量、当前摄入比例、估算热量、编辑入口。主列表不默认塞入蛋白质、脂肪、碳水等额外指标，避免分散注意力。

合计明确标注“约”，例如“约 525 千卡”。可折叠查看“估算范围 430–680 千卡”及影响因素；区间是模型估算范围，不能表述为统计学置信区间。上下界应与分项口径一致。

示例数据（仅用于设计，不构成营养建议）：米饭约 150 克 / 175 千卡；鸡肉约 120 克 / 240 千卡；炒青菜约 150 克 / 110 千卡，含估算用油；总计约 525 千卡。

对于用油、糖、酱料等看不清的部分，说明是否已计入，避免菜品热量与单独油脂重复累加。混合菜默认以整道菜计算，可展示主要食材说明，不伪造每种隐藏食材的精确重量。

低把握时只追问影响最大的必要问题，例如“这是一人份还是共享餐？”。没有校准依据时不展示“准确率 98%”等数字。

底部主按钮：确认并保存。识别完成不会直接写入外部平台；保存后按用户已经开启的授权设置执行外部写入。

## 7. 食物编辑弹层

字段：名称；份量（克、毫升或常见份量单位）；实际摄入（全部、3/4、一半、1/4、自定义）；烹饪方式；热量。

“拍到的份量”与“实际吃下比例”分开，防止将剩余量当成摄入量。支持直接输入整项热量，此时标注为“手动输入”，不再偷偷按模型份量覆盖。

只修改摄入比例：在原估算上重新计算，不需要重新上传照片。修改食物名称或烹饪方式：允许重新估算，仅更新该食物，保留其他人工修改。重新估算前提示将影响哪项数据。

支持新增遗漏食物、删除误识别项。点击完成后返回结果页，合计立即更新。已有历史记录编辑时，提供保存修改和取消；取消不改变原记录。

## 8. 保存与外部写入

本机保存优先。成功后显示“已保存本餐”，可进入详情或返回今天。

各目标分开记录状态：本应用已保存；苹果健康待写入/已写入/未授权/失败；小米未接入/不支持/待写入/已写入/失败。未接入或未验证时不展示虚假的小米成功状态。

每餐具有稳定唯一标识。反复点击保存、重试上传和多端导入不能创建重复记录。修改或删除本应用创建的健康样本时，需维护外部样本映射；跨端防重机制需在开发时验证。不能删除其他应用写入的健康记录。

苹果健康写入失败时本机记录仍有效，提示“本餐已保存，苹果健康写入失败”，允许单独重试。

小米未具备写入能力时提供“复制本餐信息”：日期、餐次、食物摘要和估算总热量。剪贴板复制不等于自动导入。打开小米应用或具体减重页面的入口，仅在实际支持跳转时展示。

## 9. 餐食详情

展示照片、日期与餐次、总热量、食物清单、用户备注、估算依据和各目标写入状态。用户可编辑、复制信息、删除本餐。

删除前明确提示影响范围。若能删除本应用对应外部健康样本，执行删除并显示结果；若外部删除失败，保留待处理状态，不宣称全部删除成功。

模型输出原始技术信息不直接展示给普通用户。保留模型版本、分析时间和人工修改来源用于排查及解释。

## 10. 历史页

顶部轻量日期选择器，默认最近七天；可打开月历跳转。选中某日后显示“已记录总摄入”、当天餐食列表及补记入口。

最近七日柱状图作为辅助信息，不压过餐食列表。没有记录的日期显示“未记录”，不画成确定的零摄入。没有每日目标时不展示达标评价。

补记允许选择过去日期，分析、确认流程与首页一致。V1 不加入社交、食谱推荐和复杂营养报表。

## 11. 设置与首次使用

首次启动直接进入今天页；在具体操作发生时请求权限，不在启动时一次索取全部权限。

模型服务：服务地址/支持的模型、密钥配置、安全连接测试、当前连接状态。个人自用版本密钥存系统钥匙串；不写入照片、历史导出或日志。公开发行需要独立处理密钥、额度和付费问题，不能把公共密钥内置到应用。

苹果健康：解释写入膳食能量的用途，开关与授权入口。V1 默认只请求必要写权限，不读取全部健康数据。关闭后不再写入新餐，旧记录的处理应另行说明。

存储与导出：本机记录数、照片空间占用、导出 CSV/JSON（可选照片）、导入恢复与去重、删除全部本机数据。照片可按需删除，保留餐食文本和热量。

隐私：明确照片会发送给所选模型服务；展示服务提供方与数据处理说明；不默认上传体重、姓名或其他不相关健康信息。关闭在线识别后仍允许手动记录。

## 12. 存储、多端与可行性边界

不自建服务器：本机数据库保存历史，应用直接连接用户配置的模型服务。没有应用账号不代表没有第三方处理；在线大模型仍需要网络和费用。

CloudKit 技术上支持用户私有数据库，但苹果 App Store 审核规则 5.1.3(ii)限制应用将个人健康信息存入 iCloud。此产品服务个人饮食与减重，因此完整历史的 CloudKit 同步必须保留为待核实需求，不能直接承诺可上架。对个人测试版本与公开发行方案，应分别确认适用条件，不把自用当作隐私限制自动消失的理由。

V1 建议本机历史 + 导出恢复 + 用户授权的苹果健康写入。苹果系统自身健康同步与应用自行把历史上传 CloudKit 是不同路径；系统同步不能保证同步本应用照片、每餐食物清单与备注。

多端完整历史是用户明确提出的需求，当前方案未解决，不应称作已满足。未来如允许合适的云服务，需追加增量同步、冲突处理、删除传播和健康样本防重设计。默认优先 iPhone；iPad 可规划阅读和编辑适配，非苹果设备不在 V1 范围内。

小米已有开放平台，但目前查阅的公开云服务接口和端侧数据定义中，未确认减重模块每餐记录的写入数据类型与 iOS 可用接入方式。须验证申请资格、账号授权、字段、目标模块呈现及是否需要保密服务端凭据。不能从有健康 API 推断支持餐食导入。

开发前应做一次最小验证：本应用写一条膳食能量到苹果健康，检查目标小米 iOS 版本是否读取、是否落到减重每餐模块、是否保留餐次与明细；再验证小米官方开放平台是否存在授权写入路径。此处仅定义验证计划，尚未执行。

## 13. 视觉与无障碍规范

基调：苹果健康式原生层级、小米式橙色主操作。浅灰背景 #F7F8FA，白色分组，主色 #FF6900；正文使用深色。橙色小字需验证对比度，不以原始品牌橙直接用于所有小字号文本。

系统中文字体；正文建议 16–17 pt，标题 28–34 pt，核心热量 44–52 pt。横向边距约 20 pt；分组间距约 24 pt；同组靠间距和分割线区分，不堆叠卡片。

按钮触控区域至少 44 × 44 pt，主要按钮高约 52–56 pt。内容支持动态字体；核心按钮不遮住滚动内容。深色模式采用深灰背景和适当提亮的强调色，不直接反相。

同步状态同时使用文字与图标，不能只靠红绿颜色。VoiceOver 能读出食物名称、份量、热量与编辑动作。大字体下食物行允许换行，热量不能截断。

## 14. V1 范围与验收标准

必做：拍照/相册、多图同餐识别、分项与总量、摄入比例调整、增删编辑、草稿与失败重试、本机历史、手动记录、导出恢复、可选苹果健康写入、清晰的外部状态。

待验证：小米减重每餐自动写入、完整历史 iCloud 同步、所有目标设备上的多端行为。未验证项不能作为首版交付承诺。

后续候选：包装食品条码、常吃餐复用、小组件、更多营养素、语音补充、端侧模型。暂不加入社区、课程、复杂运动建议。

验收：一张餐食照片得到可编辑的分项结果；合计等于当前摄入分项之和；识别失败不丢草稿；改份量不强迫重拍；历史能找到并修改本餐；未记录日不误报零摄入；外部失败不影响本机保存；重复重试不生成重复餐食；权限被拒绝时仍可完成手动记录。
